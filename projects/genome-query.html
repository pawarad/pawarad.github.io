Project

Asking a genome database questions in plain English

A web app that turns a question into a database query, runs it on whole-genome data that never leaves our servers, and shows the answer with where it came from.

The problem

A whole-genome sequencing study produces a lot of results per sample: copy number, tumor fraction, structural variants, small variants. They sit in separate files from separate tools. Answering a simple question such as "which samples have a gain on chromosome 8q and a high tumor fraction?" usually means asking a bioinformatician to write a script. The wait is days, and the person who knows the biology is not the person who can query the data.

How it works

  1. Pipeline outputs are loaded once. Parsers read results from tools such as ichorCNA, TITAN, SvABA and HaplotypeCaller and store them in a structured, normalized Postgres database.
  2. You ask in plain English. No query language, no file paths.
  3. The model sees the schema, not the data. The relevant table and column descriptions are retrieved and given to a language model, which writes a database query.
  4. The query is checked, then run. It is read-only, and it runs on the local database.
  5. You get the answer and its source. Results come back as a table, with the query shown so it can be checked.

We chose a database query over embedding the data into a vector store. Genomic results are numbers, coordinates and categories, and questions about them need exact filters and counts. A database returns those exactly. Similarity search over text tends to return plausible but wrong answers.

The whole system runs offline, on our own infrastructure. Sequence data and patient-level results are never sent to an outside service.

An example

The question below is illustrative, not real data.

Ask: Which samples have a gain on chromosome 8q and a tumor fraction above 0.2?

The tool: writes a query joining the copy number and tumor fraction tables, runs it, and returns the matching sample list with the query attached.

Why it is useful in a clinical research setting

  • Faster questions. Clinicians and biologists can explore a cohort directly, so a question that took a request and a wait takes a minute.
  • Consistent definitions. Every sample is stored the same way, so a "high tumor fraction" means the same thing across studies.
  • Checkable answers. Each result shows the exact query behind it, so an analyst can confirm it rather than trust it.
  • Privacy by design. The data stays inside the institution's network, which is the setting where patient genomic data has to stay.
  • Frees up analysts. Routine cohort questions stop competing with the method development that needs a bioinformatician.
